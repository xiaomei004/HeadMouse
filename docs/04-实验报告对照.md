> （5）安装 eViacam
> （6）头动控制电脑，实现鼠标的移动、单击、双击。

## 2. 两个常被问到的问题

### Q1：停下来只点一次，再点必须移动位置，符合实验要求吗？

**符合。** 实验要求的是"实现鼠标的单击、双击"，即**可预期、不误触**的点击触发，
没有规定"停住就连续触发"。相反，如果停住会一直点，就是缺陷：

- 真实鼠标的点击是"按下—抬起"的**离散动作**；
- 停留型点击（dwell click）如果把"停留"直接当成触发条件，就会以 `DWELL` 的节奏
  无限连点 —— 连续打开多个链接、把文件拖走、误关窗口；
- 因此所有主流实现（eViacam、Windows 自带眼控、iOS 切换控制）都要求
  "触发一次后必须先离开再回来"。本项目用"光标净位移 ≥ 90 px"来表达"离开再回来"，
  并在界面实时显示 `LOCKED / ARMED`，把内部状态暴露给用户。

这条正好可以写进报告的"难点与解决"：**停留时长阈值与连点误触之间的平衡**。

### Q2：脸移多少光标就走多少，而不是"脸偏左就一直左移"，符合实验要求吗？

**符合，而且这是 eViacam 的默认做法。** 头动鼠标有两种映射律，都属于"头动控制鼠标"：

| | 位置映射（本项目默认） | 速度映射（`T` 切换） |
|---|---|---|
| 关系 | 偏移量 → 光标位置 | 偏移量 → 光标速度 |
| 表现 | 脸偏多少走多少，脸回中光标回原点 | 脸偏左就一直左移，回中才停 |
| 类比 | 触摸板绝对定位 / eViacam | 摇杆 / 触摸板相对定位 |
| 适合 | 精确指点、短距离 | 大屏、长距离 |

两种都已实现，运行时按 `T` 切换，可以现场对比两种映射律的操作负荷（这也是
人机交互里"绝对定位 vs 相对定位"的经典对照实验）。如果报告里要选一种作为结论，
建议：**单屏 + 精确任务用位置映射，多屏/大屏用速度映射**。

## 3. 可直接用于报告的素材

**难点与解决（逐项举例）**

1. 指定软件 eViacam 在本机启动即崩（`0xc0000005`，Qt5/OpenGL 与核显驱动不兼容），
   换路径、改兼容模式、重装 CRT 均无效 → 按同样交互思路自主实现，同样的交互目标、可控的代码。
2. 初版光标移动迟钝且只往左上跑 → 定位为"背景静止纹理稀释 + 平均值被离群点污染 +
   光流累计误差"三重问题，通过"脸框内撒点 + 中位数 + 脸框锚定融合"解决，
   静置漂移由 165 px 降到 17 px。
3. 停留点击会连点 → 引入"净位移重新武装"，并把状态可视化。
4. 窗口失焦后无法用 ESC 停止，鼠标被程序占死 → 改用 `GetAsyncKeyState` 全局急停，
   并加入"人工接管自动暂停"，任何时刻都能把控制权抢回来。
5. 头部**旋转**与**平移**在光流里难以区分，点头会被当成光标下移 → 目前靠死区与
   重新锁定缓解，属于该方案的固有局限。

**心得体会（两三句）**

> 体感交互的门槛不在"能不能识别"，而在"抖动、延迟、误触发"这三件小事上：
> 识别率 99% 的系统，只要有 1% 的抖动，用户就不敢用。真正让光标听话的，
> 是中位数、死区、锚定这些看起来很土的办法，而不是更复杂的模型。
> 另外，任何持续接管输入设备的程序都必须留一个不依赖 UI 的一键逃生口 ——
> 这是被"鼠标锁死在屏幕中心、只能强制关机"教会的。

## 4. 演示步骤（拍照/录屏用）

1. 双击 `启动头控.cmd`，等画面里出现黄色人脸框（`FACE 0.9x`）
2. 把光标放到桌面图标附近，按 `空格`，屏幕上出现 `TRACKING - POSITION`
3. 头部左右偏，光标跟着走；停住 0.8 s，底部进度条走到头 → 桌面图标被单击
4. 按 `X` 切双击 → 再停一次，界面 `clicks:N (S1/D1)` 计数变化
5. 按 `T` 切速度映射 → 头偏左，光标持续左移
6. 按 `F8` 暂停（可先把焦点切到别的窗口，证明全局键有效）
7. 拍照时保证画面里能看到人脸 + 摄像头窗口 + 光标位置
