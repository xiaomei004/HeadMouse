# 问题排查记录

按发生顺序记录，每条都是「现象 → 定位 → 根因 → 解决」。踩过的坑比结论更有参考价值。

---

## 1. eViacam 一启动就崩，程序自己消失

**现象**：双击 `eViacam.exe`，鼠标转两圈，窗口不出现，进程消失；Windows 事件日志里有
`APPCRASH`，异常代码 `0xc0000005`（访问冲突），出错模块在 `Qt5Core.dll` / `opengl32sw.dll` 之间飘。

**定位**：
- 换英文路径（中文路径是常见元凶）→ 仍然崩
- 右键属性 → 兼容性 → Windows 7 兼容 + 禁用视觉主题 + 以管理员身份 → 仍然崩
- 删掉 `config`、以 `--safe-mode` 启动 → 仍然崩
- 事件日志显示崩溃发生在 OpenGL 上下文创建阶段，本机是 Intel 核显 + 混合输出

**根因**：1.7.2 这版 Qt5 用的旧版 ANGLE / `opengl32sw.dll` 与本机显卡驱动不兼容，
属于环境问题，不是配置问题。

**解决**：不修了。按同样的人机交互思路自研（本项目）。
**教训**：判断"值不值得修"比"能不能修"更重要 —— 一个 GUI 崩溃卡了 40 分钟，
而核心诉求（头动控制鼠标）是可以自己实现的。

## 2. 把代码粘到 `>>>` 里，只执行了第一行

**现象**：`python` 进入交互式环境后粘贴多行脚本，只有第一行生效，后面全在等输入。

**根因**：REPL 逐行求值，粘贴多行 `for`/`def` 需要空行结束，字符一多就断在奇怪的位置。

**解决**：一律写成 `.py` 文件再 `python 文件名` 运行。
**教训**：超过 3 行的代码就不要进 REPL。

---

## 3. 启动脚本双击后只弹出一个 Python REPL

**现象**：`启动头控.cmd` 双击，黑窗口一闪，接着出现 `>>>` 提示符，程序没跑。

**根因**：文件是用 LF 换行的。cmd 解析批处理时依赖 CRLF，遇到 LF 会把两行拼成一行，
`setlocal` 后面的语句全部失效，最后 `"%PY%" "head_mouse.py"` 被拆散。

**解决**：`.cmd` 必须 **CRLF** 换行。
**教训**：Windows 批处理 = CRLF + GBK，两条都得守。

---

## 4. 中文括号导致 cmd 报"命令语法不正确"

**现象**：脚本里写了 `echo （1）等待摄像头窗口弹出`，cmd 报 `命令语法不正确` 或直接截断，
后续语句不执行。

**根因**：cmd 按 ANSI/OEM 代码页逐字节解析，UTF-8 编码的中文在 936 代码页下变成乱码字节，
其中 `（` 的某个字节恰好是 cmd 的元字符（`&`、`|`、`>` 一类），于是把命令切断了。

**解决**：`.cmd` 文件用 **GBK** 编码保存（`chcp 936` 与之一致），并避免在 `echo` 里用全角括号。
**教训**：`.py` 用 UTF-8，`.cmd` 用 GBK，同一个项目里两种编码并存很正常。

## 5. 控制台中文输出乱码 / 程序在管道里直接异常

**现象**：设置 `PYTHONUTF8=1` 后，`print("中文")` 在 cmd 窗口里是乱码；
被 `| tail` 之类的管道接走时，甚至抛 `UnicodeEncodeError` 或直接卡住。

**根因**：Python 3.11 的 stdout 编码跟随 `PYTHONUTF8`/`PYTHONIOENCODING`，
而 cmd 窗口的代码页是 936（GBK）。UTF-8 字节按 GBK 解释 = 乱码；
反向（GBK 输出到 UTF-8 期望）则可能编码失败。

**解决**：启动脚本里显式 `set PYTHONUTF8=0` + `set PYTHONIOENCODING=gbk` + `chcp 936`，三者对齐。

## 6. OpenCV 5.0 没有 `haarcascades`，人脸检测模型也下不下来

**现象**：`cv2.CascadeClassifier(cv2.data.haarcascades + "haarcascade_frontalface_default.xml")`
报 `can't open file`；去 GitHub 下 YuNet 的 `face_detection_yunet_2023mar.onnx`，
拿到的只有几百字节的 LFS 指针文本。

**根因**：opencv-python 5.0 的精简包里已经不含 `haarcascades` 目录；
GitHub 对大文件用 LFS，直接访问 `raw.githubusercontent.com` 拿到的是指针文件。

**解决**：改用 `media.githubusercontent.com` 镜像地址下载真实二进制，得到 232 KB 的 onnx，
用 `cv2.FaceDetectorYN.create()` 加载。

## 7. 模型加载失败：`cv2.dnn` 打不开中文路径

**现象**：模型放在 `桌面/大四/人机交互——徐承志/实验/4/models/yunet.onnx`，
`FaceDetectorYN.create()` 直接抛异常，中文路径。

**根因**：`cv2.dnn` 的模型加载走 `fopen` 窄字符接口，不做 UTF-8 → 宽字符转换。

**解决**：先把模型复制到 `%TEMP%/head_mouse_yunet.onnx`（纯英文）再加载，
见 `ascii_model_path()`。

## 8. 头往哪偏，光标动得很慢，而且只会往左上跑（核心问题）

**现象**：最初版本能跑，但光标移动幅度只有头部的 1/5，而且无论往哪个方向偏，
光标都偏向屏幕左上，停不下来。

**定位**：
- 打印每帧 `dx, dy` 与参与计算的点数：发现 160 个点里有 120+ 个落在背景（墙、柜子、
  显示器边框）上，它们的光流位移恒为 0
- 打印单点位移分布：大部分点是 (0,0)，少数点是 (−20,−18) 之类的离群值
- 去掉前后向校验后离群点更多 → 确认是跟踪点质量的问题，不是映射增益的问题

**根因**：
1. **点撒错了地方** —— 在全画面撒角点，静止背景占比过高，平均位移被稀释 → 慢；
2. **用了平均值** —— 几十个朝左上的离群点（光流搜索窗偏好方向 + 镜面反射）把均值拽偏 → 只往左上；
3. **光流是增量估计** —— 每帧 0.1 px 的偏差持续累加，10 秒后就是上百像素 → 漂移。

**解决**（三处一起改，缺一不可）：
- `FaceBox.mask()`：只在人脸框内缩后撒点 → 160 个点全在脸上；
- 位移取**中位数**而不是平均值 → 抗离群点；
- 加入**脸框锚定融合**（`BETA = 0.12`）→ 消掉累计漂移。

**效果**：静置 10 秒漂移从 −165 / −224 px 降到 −17 / −15 px，锚定残差 1.6 px，
人脸检出 240/240 帧，帧率 29 fps。

## 9. 光标静止时自己抖、还时不时误点

**根因**：摄像头噪声 + 人脸检测框 ±2 px 抖动 → offset 在 ±2 px 之间抖 → 光标抖；
`still_t` 永远累加不到 `DWELL`，但偶尔抖得小一点就攒够了 → 误点。

**解决**：`DEAD = 1.6 px` 死区（按比例削减，不是硬截断）+ `SMOOTH = 0.3` 的 EMA；
静止判定用"单帧位移 < `STILL_PX`" 而不是"offset 不变"。

## 10. 一按空格开始，光标立刻点了一下

**现象**：按空格后 0.8 秒，光标所在位置被点了一下，用户在 `armed` 语义上还没做任何动作。

**根因**：开始时 `armed = True`，`still_t` 从 0 开始累加，头还没动就满足了停留条件。

**解决**：开始时 `click_pos = 当前光标位置`、`armed = False`，
必须先让光标净位移 ≥ 90 px 才允许第一次点击。

---

## 11. 按空格后光标跳到屏幕中心；小窗口时也绕着屏幕中心动

**现象**：程序窗口只是个小窗，但一按开始，光标跑到屏幕正中；之后无论窗口在哪，
光标都以屏幕中心为原点运动。

**根因**：映射写死成 `光标 = 屏幕中心 + k·offset`。窗口位置和光标原点根本没关系，
是概念混淆 —— 程序窗口只是一块"监视器画面"，光标活动范围本来就该是整个桌面。

**解决**：`原点 = 按下开始时的光标位置`（`GetCursorPos`），按下前后零位移；
`O` 键可重取原点；`--origin center` 保留旧的屏幕中心行为。

**教训**：用户说"应该在窗口中心"时，真实诉求往往是"别让我丢失光标"，而不是"把坐标系改到窗口"。

## 12. 窗口不在最前时，鼠标被锁死在屏幕中心，只能关机（最严重）

**现象**：开着人脸控制，点开别的窗口做事，光标每帧被强行拉回屏幕中心，
物理鼠标推不走；由于窗口失焦，`空格`、`ESC` 全都没反应，最后只能强制关机。

**定位**：
- `cv2.waitKey()` 只在窗口拥有焦点时才收键 → 失焦 = 按键全失效；
- 每帧 `SetCursorPos(屏幕中心 + offset)`，offset≈0 时等于把光标钉在中心。

**根因**：三个问题叠加 —— 原点设在屏幕中心（第 11 条）+ 没有全局急停 + 没有"人在抢鼠标"的检测。

**解决**（三道闸，任何一道都能救回来）：
1. **全局急停**：`F8` 暂停 / `F12` 退出，用 `GetAsyncKeyState` 轮询硬件按键状态，
   与窗口焦点无关；
2. **人工接管检测**：本帧设置光标**之前**读 `GetCursorPos`，与上次设定值差 > 90 px
   就判定"真人在拖鼠标"，立即暂停并交还；
3. **原点改到当前光标位置**，从根上消除"光标被拽到中心"的观感。

**教训**：任何会持续接管输入设备的程序，都必须有一个**不依赖 UI 焦点**的停止手段。
顺序也很关键：先判断接管，再设置光标；反过来永远检测不到。

## 13. 检不到脸时，跟踪点跑到背景上，光标乱飞

**现象**：人离开座位 / 转身，光标开始朝一个方向狂飙。

**根因**：脸框丢失后 `mask()` 退回固定 ROI（画面中央），把背景纹理当成了头。

**解决**：`box is None and fb.enabled` 时**冻结光标**（跳过整个映射与点击流程），
并在 2.5 秒后自动暂停。UI 顶部显示 `FACE LOST - cursor frozen`。

## 14. 切到双击模式，clicks 计数没区别

**现象**：`X` 键切换单击/双击，界面上 `clicks` 每次仍然 +1，看不出区别。

**根因**：计数器只记"触发了几次"，不区分这一下是单击还是双击 —— 显示层的信息量不足，
不是功能坏了（双击确实发出了两下 `LEFTDOWN/UP`）。

**解决**：拆成 `clicks_single` / `clicks_double` 两个计数，界面显示
`clicks:总 (S单/D双)`，总点击数 = 单 + 双×2；控制台每次点击也打印明细。

## 15. 停下来只计一次点击，再点必须移动 —— 是 bug 吗？

**结论**：不是 bug，是 dwell click 的必要设计（见 `docs/01` 第 8 节）。

真实的鼠标点击是"按下—抬起"的离散动作；如果停留就能无限触发，人会看到光标在
同一个位置以 0.8 s 的节奏连续点击（比如连续打开好几个链接、把图标拖走）。

因此引入 `armed`：点击后必须让光标**净位移 ≥ 90 px** 才允许下一次。
界面上一整行 `move:xx/90 px  LOCKED/ARMED` 就是在告诉用户"现在能不能点"。

如果你就是要"停在那里连点"（例如做计数器演示），把 `REARM_PX` 调小到 5 即可，
但不建议日常使用。

## 16. 速度模式一开就"飞"到屏幕边缘

**现象**：切到速度映射（`T`），头稍微一动光标就窜到角落，完全没法用。

**根因**：线性映射 + 满速 1500 px/s、满速区只有 26 px。
偏移 20 px（相当于静止时头部抖动的量级）就已经给出 54% 满速 = 810 px/s。

**解决**：换成 `v = VMAX·g^1.5`（`g` 为 0~1 的归一化偏移），满速降到 650 px/s、
满速区拉宽到 45 px。20 px 偏移时从 810 px/s 降到 101 px/s，慢速段变得可用；
`1/2/3` 键现在同时给位置模式行程和速度模式满速（380/650/1000 px/s）。

## 17. 速度模式下"人工接管"被误判，一秒就自动暂停

**现象**：只要一进速度模式，跑一两帧就打印 `[自动暂停] 光标被手动移动`，
日志显示偏差 ~99 px，可根本没人碰鼠标。

**定位**：把 `Cursor.sync()` 的偏差打出来，发现偏差随移动速度变大 —— 速度越快越容易误判。

**根因**：`mouse_event(MOVE)` 之后立刻 `GetCursorPos()`，读到的**不是**新位置。
输入队列有 1~2 帧延迟，鼠标加速还会改变实际增量，于是 `last`（我们以为的位置）
是旧的，下一帧一比对就差出几十上百像素。

**解决**：
1. `last` 不再靠读回，而是**按自己下发的增量推算**（`last += (ix, iy)`）；
2. 每帧开头读一次真实坐标：偏差在容差内 -> `adopt()` 校准，认为是我们自己动的；
3. 偏差超过 90 px 要**连续 3 帧**才算人工接管（单帧偏差可能只是队列延迟）。

**教训**：判断"是不是别人动的"，不能拿"我刚设的值"当基准——
你要拿"我预期的值"和"系统实际的反馈"比，而且给延迟留一帧的余量。

## 18. 光标太小、换个背景就找不到

**现象**：头控时光标在浅色桌面上几乎是隐形的，用户必须不停"晃一下"找它。

**根因**：Windows 系统指针固定 32 px（DPI 缩放后约 40 px），颜色随主题，
Windows 的"光标大小"设置写注册表 `CursorBaseSize`，要重新登录才生效。

**解决**：不动系统设置，在指针周围叠一个分层窗口画准星（黑-琥珀-黑圆环 + 四向刻度），
`WS_EX_TRANSPARENT` 保证点击穿透，`H` 键可关。实现细节见 `docs/01` 第 13 节。

**踩到的坑**：`ctypes` 调 GDI 时没写 `argtypes`，64 位句柄超过 `int32` 就抛
`OverflowError: int too long to convert`，表现为"光环偶尔能用偶尔不能用"
（句柄值小时正常）。给每个函数显式声明 `c_void_p` 后才稳定。
